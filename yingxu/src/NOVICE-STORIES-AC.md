### 最重要的剩余用户痛点

1. **从小说到“可拍的视觉资产”仍有人工断层。** 章节、人物、场景和参考管理已通，但新手仍须外部获取角色图/分镜图，并手工决定镜头覆盖；下一阶段最有价值的是有预览和明确采用的编剧/图像服务接入，而不是继续加空生成按钮。
2. **还不能邀请朋友从公网验证真实推理。** 域名、正式身份/存储/备份和真实H3验收池未交付；网页模拟速度或CPU剪辑速度不能用作模型生成承诺。
3. **粗剪完成后，精修仍要外部剪辑工具。** 没有波形拖拽、关键帧/淡入淡出、转场、调色和EDL/FCPXML；字幕要手工校时。当前能检查故事节奏并交付粗剪，不能称全自动专业成片。
4. **大素材恢复和跨设备持续工作仍有额外步骤。** 云版本显式保存、浏览器草稿与云版分别存在；上传中断不能断点续传，完整ZIP上限小于云上传上限，用户需单独备份大文件。
5. **两账号是隔离测试，不是共同制片。** 暂无项目共享、团队角色、多人实时编辑/冲突合并或带讨论线程的审片批注；生成任务恢复核对与账户/API身份仍依赖管理员。

以上是功能与验收边界，不表示已经批准新供应商调用、云部署或新增费用。

案例 A「雨夜信箱」：快递员把迟到十年的信送到废弃车站。两章、两场、固定角色、雨衣造型、竖屏。
案例 B「咖啡店」：一句话五秒产品氛围镜头，无人物和参考也能预检。
案例 C「人物动作与声音」：角色图片、视频动作 1–4 秒、音频 1–3 秒分别作为输入；不是剪辑背景音乐。

## 本轮修改依据

专业制作先把场戏具体落实到镜头，并记录有助于拍摄/剪辑覆盖的动作和机位；本项目据此保留章→场→镜结构，把画面、景别、运镜、角色造型分开，再让用户检查实际发送给模型的文本。[Adobe shot list](https://www.adobe.com/uk/creativecloud/video/discover/shot-list.html)

预检、未保存状态、模拟标签、原prompt保留、错误位置与撤销，采用“状态可见、用户控制、错误预防、减少记忆负担”的原则。[NN/g usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)

React Flow 本身不替业务安排节点布局；Inkseq 继续使用列式排布和矩形避让，只给新节点找空位，不为一次布局引入额外依赖或覆盖用户已移动坐标。[React Flow layouting](https://reactflow.dev/learn/layouting/layouting)

## 分级结论

- 可实用的创作组织：原文保存与可编辑拆场、用户章节/场/镜管理、角色造型和参考图复用、关联图、撤销、备份。
- 已接 API 的流程：账户私有项目版本、媒体上传/派生/私有读取、计划预检、幂等单镜和批次、模拟回填，以及真实CPU章节粗剪、独立音轨与可选手工字幕烧录。后端每个新增业务字段仍须按真实 UI 合同验收，不能只靠简化fixture。
- 当前未接的自动创作：LLM写作、人物/场景图生成、Marble/3D、自动专业剪辑和发布。H3真实模型可用性、速度、画面与音频质量仍需独立云端验收。

优先级更新：角色合同、双镜静音/有声粗剪、选段、同次声音、SRT与中文烧录均已闭环；后续Chrome工具从真实鉴权下载链接保存MP4，实际落盘/SHA/解码已确认，早期监听超时的记录作为历史保留。下一阶段先完成正式部署与真实推理验收，再按中央API目录核对编剧/图像服务，补小说到视觉资产的人工断层。不能用模糊“AI生成”按钮掩盖空接口。
